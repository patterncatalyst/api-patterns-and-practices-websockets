## Learning objectives

By the end of this chapter you can:

- Recognize idle-timeout as a liveness trap when a server's own outbound ping resets the same clock meant to detect a silent peer.
- Distinguish a reconnect loop from a resumed stream, and know when `StatelessBackplane`'s stateless mode silently drops a gap-era event.
- Catch a size-like parameter's inverted default, such as `asyncio.Queue(maxsize=0)` meaning unbounded rather than zero-capacity.
- Avoid turning an auth failure response into a signature oracle by collapsing distinct JWT failure modes into one close code.
- Treat `contracts/handling-event.proto` and `asyncapi.yaml` as two contract halves needing an explicit parity gate, not a single source of truth assumed to stay in sync.

## Why this matters

Every anti-pattern in this chapter already happened somewhere in this site's own examples, not as a hypothetical a tutorial invents to sound thorough. `examples/part4-connection`'s heartbeat config shipped with the idle-timeout trap before `HeartbeatLivenessSweep` existed to fix it. `examples/part4-connection/verify.sh`'s Step 5 comment exists because someone reached for `OUTBOUND_QUEUE_MAXSIZE=0` expecting the smallest possible queue and got the opposite. `examples/part4-backplane`'s stateless mode is the "before" picture Chapter 15 built, specifically so Chapter 16 would have something to fix. Eight mistakes make up this chapter, grouped by where they tend to surface — a connection's lifecycle, the bounds around how much a server will hold, the authentication boundary, the wire schema two stacks share, and the design instinct that treats a socket like something it isn't. Each one is cited against the chapter or file where this site caught it live, not asserted from a general principle, because the whole point of closing Part 6 with this chapter is that every claim in it already has a receipt.

## Lifecycle: mistaking activity for liveness

**Idle-timeout as a liveness detector.** `examples/part4-connection`'s Quarkus config looked complete on paper: turn on `auto-ping-interval` so pings go out, set `quarkus.http.idle-timeout` so Vert.x tears down a connection that's gone quiet, done. Chapter 14 proved it wasn't. Vert.x's idle-timeout resets on *any* read or write on the connection, and the server's own outbound ping is write activity on that same connection — every 20 seconds, whether or not the peer has answered a single one of them, the server resets its own idle clock by sending the next ping. A silent peer and a healthy one look identical to that mechanism, because it was never watching for a pong; it was watching for traffic, and the server guarantees there's always some. `examples/part4-connection/verify.sh`'s `raw_silent_client_close_wait` probe — a hand-written WebSocket handshake over a raw TCP socket that never pongs, never closes, never sends anything else — stayed `STILL_OPEN` against the Quarkus app well past its configured idle-timeout window before `HeartbeatLivenessSweep` existed to catch it. The fix isn't a bigger timeout; it's a different signal. `HeartbeatLivenessSweep` tracks `LAST_PONG_AT` per connection, stamped on open and only ever advanced by an actual pong, and a separate `@Scheduled` bean sweeps every open connection on its own clock, closing anything silent for longer than a configured window. The lesson generalizes past Quarkus: a tempting liveness check is tempting because it's one config line, and it's wrong whenever the thing it watches — traffic — is something the server itself can produce without the peer's participation.

**Stateless reconnect assuming no gap.** A reconnect loop with backoff and jitter, the kind Chapter 10 built on both stacks, solves "the client notices its connection died and gets a new one." It solves nothing about what happened during the gap, and `examples/part4-backplane`'s default profile is built specifically to make that distinction impossible to miss. `StatelessBackplane`'s `publish` fans an event out to whatever's subscribed *right now* and forgets it the instant that call returns — no queue, no log, nowhere for a disconnected client's missed event to wait. `verify.sh`'s Stage A proves the consequence live: connect, receive the three-event seed, disconnect, inject a new event through the same instance, reconnect with `?afterEventId=<last seen>` — the exact resume call Chapter 10's clients already know how to make — and the injected event is gone. Not delayed, not buffered: gone, because `replayFor`/`subscribe` never had anywhere to look it up from. The HTTP inject call that puts the event on the wire returns `202 Accepted` the whole time; nothing errors, nothing retries, nothing alerts. A reconnecting client ends up with fewer events than it would have had if it had never disconnected, and nothing in stateless mode's own behavior surfaces that difference. The mistake isn't running stateless mode — Chapter 15 is explicit that it's the right tool when a stale value is harmless or a full resync is cheap elsewhere. The mistake is assuming a reconnect loop recovers data by itself, for a feed where every event is an individually significant fact (a booking's handling-event history, in this example) and there's no side door to re-fetch what the gap cost. That gap needs a place to retain events and a way to answer "after X" against it — Chapter 16's Kafka-backed mode — not a cleverer client.

## Bounds: the zero that isn't zero, and the broadcast that isn't free

**`asyncio.Queue(maxsize=0)` meaning unbounded, not zero-capacity.** `examples/part4-connection`'s `OutboundQueue` sits on top of `asyncio.Queue` to bound how many not-yet-sent frames a slow client's connection is allowed to accumulate before the server closes it or drops work. `verify.sh`'s Step 5 comment documents the trap directly: `OUTBOUND_QUEUE_MAXSIZE=0` does not mean a zero-capacity queue that trips backpressure on the very first send — that's `asyncio.Queue`'s own documented behavior, `maxsize <= 0` disables the bound entirely, the opposite of what "0" means for almost every other size-like parameter in the same codebase. A developer reaching for `0` expecting the smallest possible queue gets the one value that guarantees backpressure never trips at all — the exact failure mode a bounded queue exists to prevent, self-inflicted through a misread environment variable. `verify.sh` can't even use the same deterministic-trigger trick on both stacks for this reason: Quarkus's guard compares `pending.get() >= maxPendingSends`, so `0` trips immediately, but the Python harness has to use `OUTBOUND_QUEUE_MAXSIZE=1` instead, because `0` on that side means the opposite of what it means on the Quarkus side for the same-looking knob. The generalizable mistake is trusting that a size-like parameter's zero value means "nothing fits" without checking the primitive underneath it — it's exactly backwards for a standard-library bounded queue, and the only way this site's own test harness caught it was running the trigger live and watching Python's queue refuse to overflow at the value that worked for Quarkus.

**Unbounded fan-out across instances.** `examples/part4-backplane`'s Chapter 18 scale-out proof — an event injected through instance B reaching a client connected to instance A — works by having every instance subscribe to the same Kafka topic or Redis channel. That's the fix, and it has a cost worth sizing before it surprises anyone in production: a backplane with N instances subscribed does roughly N times the deserialize-and-filter work per injected event, regardless of how many of those instances have a client waiting at all. If a booking has exactly one connected client on instance A, injecting one event still wakes up every other instance's consumer, which checks its local connection registry, finds nothing, and discards the record — cheap per instance, but not zero, and it scales with instance count, not with how many clients are watching. The anti-pattern isn't adopting a backplane; `examples/part4-backplane/PROTOCOL.md` and Chapter 18 are explicit that sticky sessions alone can never solve "an event injected on one instance reaches a client connected to a different one," because sticky sessions say nothing about where an event originates. The anti-pattern is treating a backplane topic as an unbounded broadcast domain scaled by the number of application instances rather than by how the data is partitioned — which is why `examples/part4-backplane` keys every record by `bookingId` even on a single-partition topic, so a production deployment can shard that broadcast domain down before the N-times multiplier turns into a real cost instead of an invisible one at a handful of instances and a handful of bookings.

## Security: authenticating too late, and answering too precisely

**Collapsing a real auth decision into something a prober can mine for information.** `examples/part4-connection`'s `handlingEvents` channel has a structural problem before it has a security problem: a browser's `WebSocket` constructor has no way to attach a custom `Authorization` header to the opening handshake, by design, so the bearer token has to travel as a `?token=` query parameter instead — which means it ends up in access logs, browser history, and proxy traces the way a header rarely does. Chapter 17 names that trade-off rather than hiding it and leans on a short TTL and `wss://` to make it tolerable, but the sharper anti-pattern sits one layer deeper, in how a failed token gets reported. `app/auth.py`'s `AuthError` and `JwtHs256.VerificationResult` both collapse four distinct failure modes — missing, malformed, bad signature, expired — into the exact same outcome: close code `1008`, no data sent, no reason echoed to the client. A server that instead replied "bad signature" for a tampered token and "expired" for a stale-but-correctly-signed one would hand a prober exactly the two bits it needs to tell "I don't have a working key at all" from "I have a working key, I only need a fresher timestamp" — turning a signature check into an oracle an attacker can iterate against one guess at a time. The reason is still logged server-side for an operator debugging a real integration issue; it never crosses the wire to the client. The related mistake Python's `websockets` library makes easy to fall into is reaching for `process_request` to reject at the door the way an HTTP middleware would — that hook runs *before* the opening handshake completes, when no WebSocket connection exists yet, so its only return option is an HTTP response with no application close code available. `app/ws_server.py`'s `handler` accepts the handshake for every connection, authenticated or not, and closes unauthenticated ones with `1008` as the very first thing it does instead — observably almost identical to an HTTP-level rejection, but consistent with this channel's other three connection-concern close codes (`4290`, `4400`, `4408`) rather than mixing an HTTP-shaped rejection in among three WebSocket-shaped ones.

## Schema: treating the wire format like source code instead of a contract

**Reusing a Protobuf field number, or assuming a JSON key rename is free on a long-lived connection.** `contracts/handling-event.proto`'s header comment states the rule in blunt terms: field numbers are additive-only, and once assigned, a number is never reused or renumbered even after the field it named is removed. The reason isn't style — a Protobuf field carries no name on the wire at all, only a tag, so reusing field `8` after `voyage_number` is retired means an old binary message, serialized before the change, decodes under the new schema as if it carried the new field's value. That's data corruption with no parse error to flag it, because the wire format has no way to tell "this is `voyage_number`'s old bytes" from "this is the new field's bytes" once they share a tag — `buf breaking` exists specifically to catch exactly that renumbering before it ships. The JSON side of the same contract has a gentler-looking version of the same mistake: Chapter 7 is explicit that *removing* a field a client already reads, or *repurposing* an enum member's meaning in place, breaks an already-connected client the same way a reused Protobuf tag does, even though nothing about JSON's text format makes either change look dangerous the way a renumbered integer tag does. And because `contracts/handling-event.proto` and `asyncapi.yaml` are two hand-kept files describing the same `HandlingEvent`, drift between them is its own anti-pattern that neither `buf lint` nor `buf breaking` can see on its own — `scripts/check-proto-parity.py` exists as the gate that watches the seam between them: field names, required-vs-optional, and enum membership and order, checked statically on every run, because a field added to one side and not the other is exactly the kind of mistake that passes every single-file lint cleanly.

**Rejecting a client that offers no subprotocol.** Python's `websockets` library has a default that's reasonable in isolation and wrong for this channel specifically: its own subprotocol negotiation aborts the handshake outright, HTTP 400, the moment a client connects without offering one. DRQ-026 names why that default doesn't survive contact with this contract — a plain browser `WebSocket`, or a `websocat` call with no `--protocol` flag, has to keep working and fall through to JSON, not get rejected for omitting a header most hand-rolled clients never think to set. `app/ws_server.py`'s `_select_subprotocol` reimplements the negotiation by hand for exactly this reason, picking JSON as the fallback whenever nothing or only the bare `handling-events.v1` token is offered, and reserving `+protobuf` strictly for a client that asks for it. The anti-pattern generalizes past this one library default: a server that negotiates a capability (a subprotocol, a compression extension, an API version) and refuses a client that doesn't participate in the negotiation has confused "optional" with "required," and the fix is almost always the same shape — define an explicit, permissive default path for the case where nothing was negotiated, rather than letting a library's own strictness decide who gets to connect.

## Design: treating a push channel like a request/response call

**No message design, no versioning plan, because the channel "is nothing but JSON."** The deepest anti-pattern in this chapter isn't a specific bug; it's a design habit that produces most of the others. Chapter 1 opened this entire site with the structural reason a WebSocket can't be reasoned about the way a REST or gRPC call is: there's no request to pair a response against, no envelope the transport provides the way an HTTP status line or a gRPC method name does, and no natural moment to stop and ask "what happens to a client that's already connected when this changes." A team that treats a socket as "a REST response that happens to arrive more than once" tends to skip two things Chapters 6 and 7 build with intent: a message shape that carries enough of its own context to be understood standing alone, with nothing to correlate it against the request that supposedly triggered it, because there wasn't one; and an explicit answer to what counts as a breaking change on a connection that might stay open for hours, which a one-shot HTTP client never has to answer because its next request picks up whatever the server looks like by then. The two earlier anti-patterns in this chapter's schema section are consequences of skipping that design pass, not separate problems: a field-numbering rule only matters to a team that already accepts the channel has a durable client observing it over time, and a subprotocol fallback only matters to a team that already planned for a client that hasn't opted into the newest negotiation yet. Skip the design pass and every other anti-pattern in this chapter becomes more likely, because nothing forced the question of what a client already running against this channel is entitled to assume.

## On the wire

The idle-timeout trap is the clearest before/after in this chapter because `examples/part4-connection/verify.sh`'s Step 6 captured both states of the same code against the same probe. Before `HeartbeatLivenessSweep` existed, `raw_silent_client_close_wait` — a hand-written WebSocket opening handshake over a raw TCP socket, confirming the `101` upgrade and then sending nothing else for the rest of the probe window, no pong, no close — reported `STILL_OPEN` against the Quarkus app, well past the configured `idle-timeout` window, because every outbound ping the server itself sent reset its own idle clock before the window could ever expire. After the fix, the identical probe against the identical channel reports a close, timed and asserted automatically rather than eyeballed:

```
lib.sh: quarkus heartbeat probe result: CLOSED:15.8
=== Step 6: assert_eq "CLOSED" "CLOSED" "quarkus heartbeat: silent peer closed within 25s"
```

`15.8` seconds is `liveness-timeout` (forced to 5s for the test) plus up to one `sweep-interval` (1s) plus Vert.x's own ~10s closing-handshake grace — the sweep requests a close with code `4408` (`CloseCodes.LIVENESS_TIMEOUT`), but that close frame never completes its handshake, because the peer that triggered it by going silent stays silent through its own teardown; what `@OnClose` observes instead is Vert.x's abnormal-closure code `1006` once the grace period gives up waiting for an acknowledgment that was never coming. Nothing about the fix made the detection instant — it made it *bounded*, which the pre-fix configuration never was. Run it directly:

```bash
bash examples/part4-connection/verify.sh
```

Both the broken and fixed states of this exact scenario are reproducible from the same repository: check out the commit before `HeartbeatLivenessSweep` landed and the Step 6 assertion fails (`STILL_OPEN` where the harness expects `CLOSED`); on the current tree it passes, deterministically, on every run — the difference between an anti-pattern that looks correct in a code review and one that's been proven wrong against a live, non-cooperating peer.
