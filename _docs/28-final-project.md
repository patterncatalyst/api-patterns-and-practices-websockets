## Learning objectives

By the end of this chapter you can:

- Assemble the `handlingEvents` feed on both stacks against `contracts/asyncapi.yaml` and `contracts/handling-event.proto`, starting from `examples/part3-handling-events` and layering each later part's concern on top.
- Explain what connection hardening, reconnect-and-backplane, binary encoding, and observability each add to the same channel, and where in the codebase each one lives.
- Deploy the assembled system to minikube and to OpenShift Local (CRC), using the deploy assets `examples/part4-backplane/k8s` and `examples/part4-backplane/openshift` already ship.
- Verify every layered capability against the specific `verify.sh` (or `verify-minikube.sh` / `verify-crc.sh`) that proves it, rather than trusting that a later part didn't regress an earlier one.
- Read the acceptance table at the end of this chapter as a map back from "does this work" to the teaching chapter that explains why it works that way.

## Why this matters

Parts 3 through 7 built the `handlingEvents` channel one concern at a time, by design. Part 3 gets a contract-generated message flowing on both stacks. Part 4 hardens the connection, then adds reconnect and a pluggable backplane. Part 5 puts a second wire encoding next to the first. Part 6 wires in tracing, metrics, and two different test tools for two different test shapes. Part 7 moves the whole thing off a laptop's Docker Compose and onto a real cluster, twice. Each part's `verify.sh` proves its own slice in isolation, against a stack purpose-built to isolate it — part5's images strip out part4's JWT and backpressure guards specifically so a frame-size comparison isn't confused by auth overhead, and part6-observability drops part4's heartbeat and backpressure code for the same reason, to keep the trace you're reading free of any concern that isn't tracing. None of those example directories, on its own, is what a team actually ships. This final project is the view a team actually needs: the same contract, carrying every one of those concerns at once, deployed where it has to hold up under traffic. It isn't a new example to build. It's a composition exercise over six example directories that already exist, run against their own `verify.sh` scripts, because the proof that assembly doesn't break anything has to be the same proof each part already trusts — not a new claim invented for this chapter.

## The brief

Build, in order: `examples/part3-handling-events` (the contract-generated feed) → `examples/part4-connection` (JWT, error taxonomy, backpressure, heartbeats) → `examples/part4-backplane` (reconnect resume, Kafka or Redis fan-out) → `examples/part5-performance` (Protobuf alongside JSON) → `examples/part6-observability` (traces and metrics) → `examples/part6-testing` (the Newman functional-HTTP layer). Deploy the result with `examples/part4-backplane/k8s` to minikube, and separately with `examples/part4-backplane/openshift` to OpenShift Local.

There is no seventh example directory for this chapter, and that's deliberate. The contract — `operations.receiveHandlingEvent` on channel `/ws/v1/bookings/{bookingId}/handling-events`, `contracts/asyncapi.yaml` lines 76–105 — hasn't changed across any of the six parts above; neither has the shared fixture, `examples/part3-handling-events/fixtures/handling-events.json`, the three `RECEIVE`/`LOAD`/`CUSTOMS` events every stack replays in order. What changes, part over part, is what sits around that one channel and that one fixture. A reader who has worked through Parts 3–7 already has every file this project needs on disk. The work here is recognizing that `part4-backplane`'s deploy assets are the furthest-along example — they already carry the backplane, and they're what `verify-minikube.sh`/`verify-crc.sh` already exercise — and treating the five examples before it as the concerns layered on top of that same deployable shape, in the order they were introduced. Nothing here asks for a `docker compose up` or a `minikube start`; this chapter composes what each part's own README already documents, so the acceptance table at the end can cite a script instead of a claim.

## Stage 1 — contract and feed

Start with `examples/part3-handling-events`. Both stacks generate their message types from the same source: `scripts/extract-message-schema.py` inlines `components.schemas.HandlingEvent`'s `$ref`s (`HandlingEventType`, `Location`, `Money`) out of `contracts/asyncapi.yaml` into a self-contained JSON Schema, `build/handling-event.schema.json` — gitignored, regenerated on every build. Python feeds that schema to `datamodel-code-generator` to produce `app/models_generated.py`, a Pydantic v2 `HandlingEvent` model that `app/feed.py` both validates fixture events against and serializes from, with `model_dump_json(exclude_none=True)` so an absent optional field never shows up as `null` on the wire. Quarkus hand-keeps its `HandlingEvent` record and `HandlingEventType` enum to the same field and enum-member names, and checks that by-hand fidelity with `HandlingEventContractTest`, which validates every fixture-derived event against the same extracted schema and asserts the enum carries exactly the contract's 8 members, in order.

Neither stack looks up `{bookingId}` against anything at this stage — any value in the path replays the same fixed 3-event sequence, because per-booking lookup isn't this part's job. What matters is that both stacks push the identical sequence, in the identical order, with the identical optional-field omission behavior. `verify.sh` opens a connection against each stack, captures the first frame, schema-validates it, asserts it matches `fixtures/handling-events.json[0]` (the `RECEIVE` event) field by field, then cross-checks that both stacks' first frames agree on every field — comparing parsed JSON fields rather than raw bytes, since Jackson and Pydantic don't serialize object keys in the same order. Acceptance for this stage is `examples/part3-handling-events/verify.sh` printing `PASS`, which only happens if every one of those assertions holds on both stacks.

This stage is the floor everything else stands on. A reconnect resume, a Protobuf frame, a trace span — none of them mean anything if the two stacks don't already agree on what a `HandlingEvent` looks like on the wire. Confirming that agreement first, with the simplest possible stack (no auth, no backplane, no second encoding), is what lets every later stage's `verify.sh` assume the base shape is correct and go test only its own addition.

## Stage 2 — harden the connection

Move to `examples/part4-connection`, a fork of part3 that keeps the same channel and the same fixture but adds the four concerns a long-lived connection needs before it's safe to leave open in production: JWT authentication, an error taxonomy for the frames this channel shouldn't accept, outbound backpressure, and heartbeat-based liveness. All four share one property both stacks implement identically — the exact close-code numbers. Authentication failure, of any kind, closes with `1008`: `app/auth.py`'s `AuthError` and the Quarkus `JwtHs256.VerificationResult` collapse missing, malformed, bad-signature, and expired tokens into that single outcome, so a prober attempting to fingerprint which check failed learns nothing from the close code alone. Because a browser's `WebSocket` constructor can't attach a custom `Authorization` header to the opening handshake, the token travels as a `?token=` query parameter instead — `examples/part4-connection/README.md` names that trade-off rather than hiding it, and leans on a short TTL plus `wss://` to keep it tolerable.

A client frame this channel doesn't expect — it's server-to-client only — gets an in-band `{"error":{"code":"BAD_REQUEST",...}}` envelope first, then a `4400` close. A sustained outbound overrun closes with `4290`, the `CLOSE` backpressure policy's default (`DROP` exists too, but isn't this channel's default). And a peer that completes the handshake and then answers nothing, not even a pong, gets closed within a bounded window: `4408` on Quarkus via a dedicated `HeartbeatLivenessSweep` bean that tracks `LAST_PONG_AT` and sweeps on its own schedule, because Vert.x's `http.idle-timeout` resets on the server's own outbound ping and so never fires against a peer that's silent but being pinged; `1011`, the `websockets` library's own hardcoded keepalive-failure code, on Python. The two stacks agree on *when* a silent peer gets closed, not on the literal numeral, and `examples/part4-connection/README.md`'s table is explicit about that one asymmetry rather than papering over it.

`verify.sh` proves all four live: mints a JWT and confirms the authenticated path still gets the fixture's `RECEIVE` frame; asserts all four token-failure modes close with `1008` and no data; sends a malformed frame and confirms both the `BAD_REQUEST` envelope and the `4400` close; spins up one-off instances with backpressure and heartbeat thresholds forced down to deterministic trigger values and confirms `4290` and the heartbeat close both fire inside a bounded wait. Acceptance for this stage is `examples/part4-connection/verify.sh` printing `PASS`; the example's `k6/smoke.js` is a useful second signal (gated in this project's own CI, 3 VUs against each stack) but isn't required to call this stage done — `verify.sh` is the one script that actually drives all four close codes.

## Stage 3 — reconnect and the backplane

Move to `examples/part4-backplane`, which drops part4-connection's hardening to isolate this part's own centerpiece: what happens when a client disconnects and comes back, and what happens when an event has to reach a client connected to a different instance entirely. Both questions turn on the same `?afterEventId=<last seen>` resume parameter a reconnecting client already knows to send, and the answer depends entirely on which of three interchangeable `Backplane` implementations is wired in.

`stateless` mode — the default, and the one Chapter 24's anti-patterns chapter calls out directly — has no queue and no log; `publish` fans an event out to whatever's subscribed right now and forgets it the instant the call returns. A client that disconnects, misses an injected event, and reconnects with `?afterEventId=` gets nothing for that gap: not delayed, gone, because `replayFor` has nowhere to look it up. `kafka` mode fixes exactly that: the same gap-era event, replayed from the shared Kafka topic on reconnect, deduped by `eventId`. A narrow, documented timing window means a client can occasionally see that one event twice — once from the replay burst, once from the live tail — so `verify.sh` treats a raw count of 1 or 2 for that event as PASS and only a count outside that range as a real failure. `redis` mode answers the second question instead of the first: an event injected through one instance's internal endpoint (`POST /internal/bookings/{bookingId}/handling-events`) reaches a client connected to a completely different instance, over Kafka or over Redis — `verify.sh` proves this once per backplane by grepping the receiving instance's own container log for its `delivered eventId=... instance=...` line, confirming the server did the delivering, not just the client's assertion that a frame arrived.

Four app instances stay up throughout this stage regardless of which broker profile is active — `quarkus-a`/`quarkus-b` and `python-a`/`python-b` — because the fan-out proof needs two instances of each stack to inject through one and observe on the other. `verify.sh` runs three sequential `docker compose up`/`down` cycles, one per backplane mode, and prints `PASS` only if the stateless-gap proof, the Kafka-replay proof, and the fan-out proof (over both Kafka and Redis) all hold on both stacks. Acceptance for this stage is `examples/part4-backplane/verify.sh` printing `PASS` across all three scenarios — the broadest single verification run in the whole project, and the one this chapter's own deploy stage builds directly on top of.

## Stage 4 — encoding

Move to `examples/part5-performance`, which forks part4-connection but strips its four connection concerns back out — no JWT, no backpressure guard, no heartbeat sweep — specifically so a frame-size comparison isn't confused by anything else on the wire. A client picks its encoding through the `Sec-WebSocket-Protocol` upgrade header: `handling-events.v1+json` or bare `handling-events.v1` for JSON text frames (opcode `0x1`), `handling-events.v1+protobuf` for Protobuf binary frames (opcode `0x2`). Both stacks declare the same preference order, so a client offering more than one value gets the same encoding regardless of which stack answers it, and JSON wins when nothing is offered at all — this channel's pre-Part-5 default stays the default.

`contracts/handling-event.proto` (package `shipping.handlingevents.v1`) is the binary encoding's own single source of truth; `contracts/asyncapi.yaml` stays the source of truth for what the message means. Keeping those in sync by hand would be exactly the kind of drift Chapter 24 warns against — a field renamed on one side, an enum member added out of order on the other — so `scripts/check-proto-parity.py` closes that gap mechanically: it compiles the `.proto` to a `FileDescriptorSet`, parses it with `google.protobuf`'s descriptor types, and diffs field names (normalizing proto's `lower_snake_case` to the JSON Schema's `camelCase`), required/optional status, and the `HandlingEventType` enum's membership and declaration order against `build/handling-event.schema.json`. It exits 0 and prints a one-line PASS summary when everything matches, and exits 1 printing every mismatch (not just the first) otherwise — a gate `buf lint`/`buf breaking` can't replace, because neither of those tools can see the JSON Schema side of the contract at all.

`verify.sh` opens each stack twice, once offering each encoding, and asserts something stronger than "both encodings independently validate" — it decodes the Protobuf frame, converts it to the same JSON-shaped dict the `+json` path produced, and asserts every field value is identical across encodings: one message, two encodings, not two messages that happen to both pass. It then measures the `RECEIVE` event's frame size on both encodings and asserts Protobuf is strictly smaller — confirmed live at roughly 40% smaller across all three fixture events (247→149 bytes on `RECEIVE`, for example; the full per-event table lives in `examples/part5-performance/README.md`). Last, it runs `scripts/check-proto-parity.py` once, stack-independent, and asserts exit 0. Acceptance for this stage is `examples/part5-performance/verify.sh` printing `PASS` and the parity gate's own exit code being 0 — two separate checks this stage can't skip either half of, because a smaller frame that decodes to the wrong values would be a regression dressed up as an optimization.

## Stage 5 — observability and tests

Move to `examples/part6-observability`, which turns on everything the earlier parts wire but leave inert: Quarkus's `quarkus.otel.sdk.disabled` flips to `false`, Python's `Containerfile` entrypoint becomes `opentelemetry-instrument ...`, and the `lgtm` Grafana stack becomes a hard dependency rather than an opt-in profile. The finding this part exists to teach is that `opentelemetry-instrumentation-fastapi` auto-traces Python's HTTP side with zero code, but there is no `opentelemetry-instrumentation-websockets` package and the native `websockets` library exposes no OTel hook — so `app/ws_server.py` opens a manual span, `tracer.start_as_current_span("ws.handling-events.connection")`, to cover the one connection this entire project is about. Quarkus's `quarkus-opentelemetry` already auto-traces the upgrade itself, so its `HandlingEventObservabilityWebSocket#onOpen` adds a `@WithSpan` child instead, parented under that upgrade span, so both stacks end up with a span named the same thing covering the same work. Both stacks emit one structured log line per connection carrying `otel.trace_id=<32-hex>` alongside the span name, and both increment a counter, `handling_events_delivered_total`, once per event actually handed off to be sent — Micrometer on Quarkus's `/q/metrics`, `prometheus-client` on Python's `:8082/metrics`.

`verify.sh` splits its checks into HARD and SOFT. HARD — and these fail the build — means the trace id shows up in the app's own structured log line and the app's own metrics endpoint shows the counter above zero; both are synchronous checks against the app itself, no external pipeline involved. SOFT means polling Tempo's query API for that same trace id with a bounded retry (10 attempts at 3 seconds), logging the outcome either way and never failing the build on a timeout — ingest lag through a cold collector-to-Tempo pipeline is expected, especially right after `lgtm` starts, and gating a merge on that lag isn't a fair trade. Real hedges worth carrying forward rather than smoothing over: this app has no dedicated health endpoint on the Quarkus side (no `quarkus-smallrye-health` dependency), and `handling_events_delivered_total` isn't registered — so it's absent from `/q/metrics` — until a WebSocket connection has actually opened at least once, because the Micrometer counter lives in a per-connection WebSockets Next bean's `@PostConstruct`.

`examples/part6-testing` covers the other test shape this project needs and that none of the above touches: functional assertions against the plain HTTP surfaces sitting around the WebSocket channel, not the channel itself. There's no app in this directory — its Newman collection runs against `part4-backplane`'s already-running compose stack, the richest HTTP surface in the project, hitting both Python instances' `GET /healthz` and both stacks' `POST /internal/bookings/{bookingId}/handling-events` inject endpoint with schema-valid and malformed bodies, asserting `202`/`400` on Quarkus (RESTEasy Reactive's default unreadable-entity mapper rejects a bad enum value; the `HandlingEvent` record has no bean validation of its own) and `202`/`422` on Python (Pydantic v2 names both offending fields in `detail[]`). It is not wired into CI yet — `examples/part6-testing/README.md` says so directly, a later wave adds a dedicated Newman job mirroring the existing `k6-smoke` job's shape — so this stage runs standalone, by hand, until that lands. Acceptance for this stage is both `examples/part6-observability/verify.sh` and `examples/part6-testing/verify.sh` printing `PASS`; the SOFT Tempo check and the not-yet-gated Newman run are both worth watching, neither is a reason to call the stage failed.

## Stage 6 — deploy

Move the assembled system off Docker Compose. `examples/part4-backplane/k8s` is the furthest-along example's own deploy target, and it's what this project reuses rather than building a seventh deploy tree: the same four-instance topology (`quarkus-a`/`quarkus-b`, `python-a`/`python-b`) behind an ingress-nginx edge, with Strimzi managing Kafka as the primary backplane mode and a Kustomize component (`components/redis-mode`) available to flip the single `BACKPLANE_MODE` ConfigMap key to Redis instead. Kafka has to be `Ready` before the apps roll out, not after — Quarkus's `quarkus-messaging-kafka` channel is wired unconditionally, and handing its always-on consumer an unresolvable bootstrap hostname is a hard CDI failure at startup, not a soft "unreachable but resolvable" case. `scripts/install-strimzi.sh` installs the operator, applies the Kafka CR, and blocks on `kubectl wait kafka/my-cluster --for=condition=Ready` before returning, and `verify-minikube.sh` calls it in that order every time. The ingress's `proxy-read-timeout`/`proxy-send-timeout` annotations are raised past nginx's 60-second default specifically so an idle WebSocket connection survives past it — `verify-minikube.sh` holds a connection idle for 65 seconds with no traffic and asserts a late frame still arrives, proving the annotation rather than asserting it. And because instance B sits outside the Ingress entirely — its internal inject endpoint is documented as demo/internal, not public contract — the cross-pod fan-out check reaches it the way every in-cluster check in this example does, with `kubectl exec` into instance A's own pod and a curl against instance B's cluster-DNS Service name, never `kubectl port-forward`.

The OpenShift Local path carries the same topology through OpenShift-native mechanisms instead: a Helm chart built for the restricted-v2 SCC (no `runAsUser` anywhere — every container tolerates an arbitrary namespace-range UID with GID 0), Kafka from the AMQ Streams operator rather than upstream Strimzi, and edge-TLS Routes in place of the Ingress, with `haproxy.router.openshift.io/timeout: "3600s"` as HAProxy's analogue of nginx's raised proxy timeouts. AMQ Streams lags upstream Strimzi in what Kafka version it supports — the live survey behind this project found the current AMQ Streams channel supports only Kafka 4.1.0/4.2.0, so `infra/kafka.yaml` pins **4.2.0**, a recorded step-back from the 4.3.1 that compose and minikube run on upstream Strimzi 1.3.0. The pub/sub replay and fan-out behavior this project cares about is identical across both Kafka minor versions, so the step-back costs nothing this chapter tests, but it's a real, cited version skew worth knowing rather than glossing over. The idle-hold check carries over to this path too, with one caveat: HAProxy's own default tunnel timeout is already far longer than nginx's 60-second default, so a 65-second idle-hold-then-late-frame result here is a weaker proof than the same check on minikube — it confirms the `3600s` annotation is present and the socket survives, not that the annotation moved a real edge closer to where a client would actually hit it. `examples/part4-backplane/openshift/README.md` says this directly rather than letting the matching green checkmark imply a matching strength of proof, and this chapter inherits that same restraint rather than smoothing the two paths into one claim.

Acceptance for this stage is `examples/part4-backplane/k8s/verify-minikube.sh` printing `PASS` on minikube and `examples/part4-backplane/openshift/verify-crc.sh` printing `PASS` on OpenShift Local — run separately, as two distinct cluster paths, never combined into one script, matching this project's standing convention that minikube and CRC each get their own full, independently headless proof rather than one path standing in for the other.

## Where this goes next

This site is done teaching the `handlingEvents` channel; the next real-time feed is whatever the reader builds next, and the habits worth carrying forward aren't specific to shipping and cargo. Start from a contract, not a handler — `contracts/asyncapi.yaml` existed before either stack's first line of application code, and every later part's test suite had something precise to validate against because of it. Keep two stacks (or two teams, or two services) verified against that one contract rather than letting either one become the de facto source of truth — `scripts/check-proto-parity.py` is the concrete shape of that discipline, a mechanical gate instead of a code-review habit that erodes under deadline pressure. And carry forward Chapter 27's cost discipline: a WebSocket earned its place in this project because the shipping-and-cargo domain has a real reason for the server to push without being asked, not because a socket is the modern-looking default. The next system that reaches for one should clear that same bar before it clears anything else — reconnect semantics, a backplane, and binary framing are all costs worth paying only once the push itself is justified.

Verification habits are just as portable as the architecture. A `verify.sh` corpus that runs the actual assertion (open a socket, read a frame, check a close code) beats a test that only proves a process started. HARD assertions belong against the thing under your own control; SOFT, bounded-retry assertions belong against a downstream pipeline whose cold-start lag isn't a fair reason to fail a build. And a headless, scripted proof on a second cluster target is worth the hour it costs before a footer gets to claim "verified" — this project's own CRC run caught real bugs (a combined-CA bundle for TLS verification, a router that returns pod-Ready before HAProxy finishes swapping endpoints) that a Helm lint or a `bash -n` would have missed entirely.
