## Learning objectives

By the end of this chapter you can:

- Separate Chapter 2's greenfield question — which transport fits a new interaction — from this chapter's question: what a socket costs once it's already shipped and carrying production traffic.
- Itemize the operational burden a WebSocket adds, using Parts 4 through 7's own examples as receipts rather than general claims.
- Map a "reach for X instead" scenario to each of six alternatives: `EventSource`-based Server-Sent Events, long-polling, webhooks, gRPC server-streaming, plain request/response on demand, and a message broker for backend-to-backend traffic.
- Recognize the migration-away signals that mean a socket already in production is the wrong tool for the interaction it's carrying.
- Name HTTP/2 server push as a dead end for browser fan-out, so nobody on the team reaches for it expecting it to work.

## Why this matters

Chapter 2 ruled a WebSocket in for the booking page's handling-event feed, and it ended with a promise: "Chapter 27 returns to this question directly, with the fuller case built once later chapters have shown what a WebSocket costs." Twenty-four chapters of protocol, contract, two independent stack implementations, reconnection, backpressure, security, observability, and a shipped anti-patterns chapter have gone by since then. This chapter collects what all of that cost, lines it up against the same five transports Chapter 2 compared on paper, and adds the question Chapter 2 couldn't yet ask: not "which transport fits a new interaction" but "does an interaction already running on a socket still belong there."

## What Chapter 2 settled, and what this adds

Chapter 2's decision framework runs an interaction through a small number of ordered questions — does it need live updates, who has to send, who's receiving — and resolves to one of five transports or to plain request/response. That framework is still correct, and this chapter doesn't re-run it or reproduce its table. What Chapter 2 could only assert in the abstract, this chapter can now back with a paid bill: Chapters 10 through 23 built the reconnect logic, the liveness sweep, the backpressure guard, the backplane, the auth workaround, and the hand-written tracing that a socket requires and the other five transports mostly don't. Chapter 24's anti-patterns chapter is the inventory of what went wrong building exactly those pieces.

The division of labor is this: Chapter 2 answers "which transport for a new interaction, decided before any code exists." This chapter answers two different questions. First, for an interaction already running on a socket, what is it costing in code, infrastructure, and operational attention — the ledger below. Second, given that ledger, here is the fuller alternatives catalog Chapter 2 only sketched, with a concrete "instead of a socket, reach for this" scenario attached to each option, plus the signals that tell a team an already-shipped socket should migrate to one of them. None of this overturns Chapter 2's worked decision for the handling-event feed itself — that feed needs duplex, low-latency delivery, and Chapter 2's framework reached that conclusion correctly. The same framework, run against a different interaction, just as often resolves to one of the alternatives below, and a team that defaults to the socket this site builds around on every interaction will miss that difference.

## The cost of a socket you didn't need

Each line below is a cost this site's own examples paid to keep a long-lived, full-duplex connection correct and operable. None of it is hypothetical; each one names the chapter that built it and the example that proves it.

**Reconnection is application code, not protocol behavior.** Chapters 10, 15, and 16 built a reconnect loop with backoff and jitter, then discovered that reconnecting is not the same problem as resuming. `examples/part4-backplane`'s default `StatelessBackplane` mode is the visible proof: a client disconnects, an event is injected through the gap, the client reconnects with `?afterEventId=<last seen>`, and the gap event is gone — not delayed, not errored, just absent, because `StatelessBackplane`'s `publish` fans out to whoever is subscribed right now and keeps nothing for anyone who reconnects later. Fixing that gap took a second mode entirely: Chapter 16's Kafka-backed backplane, with its own topic, its own retention policy, and its own replay-and-dedup logic on both stacks. None of that exists for a transport that never promised a continuous connection to begin with — a long-polling client or a webhook receiver has no gap to resume across, because each delivery is already a complete, bounded unit.

**Liveness detection needs its own clock, because the transport's own clock lies.** Chapter 14 built `HeartbeatLivenessSweep` specifically because the obvious approach — turn on `auto-ping-interval`, set an idle-timeout, done — doesn't work. Vert.x's idle-timeout resets on any read or write on the connection, and the server's own outbound ping is write activity on that same connection, so a silent peer and a healthy one look identical to a timer that's only watching for traffic. `examples/part4-connection`'s `HeartbeatLivenessSweep` tracks `LAST_PONG_AT` per connection, stamped only by an actual pong, with a separate scheduled sweep closing anything stale. That's a dedicated bean, a scheduled job, and a close code (`4408`) that exist purely to answer a question — is anyone still listening on this socket — that SSE's and gRPC's underlying HTTP/2 connections still have to answer in their own way, but that a webhook or a long-poll never has to ask at all, because neither one holds a connection open between messages.

**Backpressure is a hand-rolled guard, not a protocol feature.** Chapter 12's `OutboundBackpressureGuard` on the Quarkus side and `OutboundQueue` on the Python side exist because a raw WebSocket gives an application nothing here beyond TCP's own flow control — a server has to watch its own send queue and decide whether to drop, buffer, or close a client that can't keep up. `examples/part4-connection/verify.sh`'s Step 5 documents the sharp edge this guard has to get right: `OUTBOUND_QUEUE_MAXSIZE<=0` means *unbounded* on Python's `asyncio.Queue`, the opposite of the zero-capacity bound a developer reaching for `0` would expect, while the Quarkus guard trips on `pending >= maxPendingSends`, so `0` behaves correctly there — the same-looking environment variable means opposite things on the two stacks, and the close code (`4290`) that signals a tripped guard is bespoke to this project, not a transport-level signal. gRPC server-streaming gets equivalent protection built into HTTP/2's own flow-control windows; a long-polling or webhook exchange never needs a backpressure story at all, because neither holds anything open long enough for a slow receiver to fall behind on.

**Fan-out across instances needs a backplane and sticky routing, not just more pods.** Chapter 17 and Chapter 18 close the gap between "a socket with a load balancer in front of it" and "a socket that actually works at more than one instance": a client has to be pinned to the instance it first connected to, since nothing about an HTTP load balancer round-robins a long-lived connection mid-life, and an event injected anywhere in the fleet has to reach whichever instance that client landed on. `examples/part4-backplane`'s cross-instance proof — an event injected through instance B's internal endpoint, delivered to a client connected to instance A, confirmed by grepping instance A's own container log for the delivering line — is the receipt that sticky sessions alone can never solve this; something has to carry the event from B to A, which is what the Kafka or Redis backplane is for. A webhook has no such problem, because the sender calls whichever endpoint the receiver registered, and a stateless request/response call has no "which instance already holds this connection" question to answer in the first place.

**Browser auth gets forced into a query parameter, because the handshake has no header slot.** Chapter 17 names the structural reason directly: a browser's `WebSocket` constructor has no way to attach a custom `Authorization` header to the opening handshake, so the bearer token has to travel as `?token=` instead — which means it ends up in access logs, browser history, and proxy traces the way a header rarely does. `examples/part4-connection`'s `handlingEvents` channel accepts this trade-off and leans on a short token TTL and `wss://` to make it tolerable, and Chapter 24's anti-patterns chapter adds the sharper detail that every one of the four token failure modes has to collapse to the same close code (`1008`) so a prober can't learn which check failed. None of that workaround exists for SSE or long-polling, both of which ride ordinary HTTP requests that can carry a normal `Authorization` header on every single call, because every call is a fresh request rather than a single handshake that has to carry everything up front.

**Tracing is a hand-written span, because the instrumentation doesn't exist.** Chapter 23 and `examples/part6-observability`'s own README state the finding directly: there is no `opentelemetry-instrumentation-websockets` package, and the native `websockets` library exposes no OTel hook of its own. `app/ws_server.py` closes that gap with a manual `tracer.start_as_current_span("ws.handling-events.connection")` call; the Quarkus side gets the HTTP upgrade traced automatically by `quarkus-opentelemetry` but still needs a hand-added `@WithSpan` child span to cover the connection-scoped work specifically. Compare that to the Python side's own HTTP surface in the same example — `opentelemetry-instrumentation-fastapi` auto-traces it with zero code, the same ecosystem that leaves the WebSocket path with nothing built in.

**Deployment needs raised timeouts and ordering constraints an HTTP API never does.** `examples/part4-backplane/k8s/README.md` documents the minikube path raising ingress-nginx's `proxy-read-timeout`/`proxy-send-timeout` past its 60-second default so an idle socket survives, and verifies that past-the-default survival live by holding a connection idle for 65 seconds and asserting a late frame still arrives. The OpenShift path carries the identical requirement through `haproxy.router.openshift.io/timeout: "3600s"` on each Route, since HAProxy's edge-TLS termination has its own idle-connection ceiling to raise. Both paths also hit an ordering constraint a stateless HTTP service never has to think about: the Quarkus side's Kafka channels are wired unconditionally, so an unresolvable Kafka bootstrap hostname crashes the app at startup rather than degrading gracefully — `scripts/install-strimzi.sh` has to block on Kafka reaching `Ready` before the app Deployments ever roll out. A webhook receiver or a plain REST endpoint needs none of this: no connection-idle timeout to raise, because nothing is held open between requests, and no rollout ordering to enforce against a dependency the protocol itself never required to be always-on.

## The alternatives catalog

Chapter 2 names these five transports plus plain request/response as the full menu. This section goes one level deeper than Chapter 2's comparison table, with the scenario that should make a team reach for each one instead of reopening a socket.

**Server-Sent Events, when the client only consumes.** Reach for SSE instead of a socket when the server is the only side that ever sends and the receiver is a browser tab you control. The warehouse dashboard from Chapter 2's opening paragraph — dozens of handling-event updates a minute, one direction only, nothing the dashboard ever needs to send back — is exactly this shape. `EventSource` gives native reconnection and a `Last-Event-ID` header the server can use to resume from where it left off, both built into the browser rather than written by the application, which is precisely the reconnect-and-resume machinery Chapters 10, 15, and 16 had to build by hand for the socket case. The cost SSE doesn't erase: it still rides one open HTTP response per client, so a server still needs to track how many of those responses are open, just without the two-way handshake, the ping/pong liveness story, or the backpressure guard a socket needs on top.

**Long-polling, when the network path doesn't trust a long-lived response.** Reach for long-polling instead of SSE or a socket when the path between client and server is known to buffer or truncate long-lived responses — some corporate egress proxies do exactly this to anything that looks like a stuck connection. Long-polling degrades to plain request/response cycles rather than failing outright: the client sends a request, the server holds it until it has something to say or a timeout expires, and the client immediately sends the next one. The cost is a full request/response cycle and fresh connection setup per update, which is wasteful at high update frequency and a non-issue at low frequency — the customs broker's integration from Chapter 2, polling a status that moves a handful of times a day, pays that cost gladly in exchange for needing nothing more exotic than plain HTTP on either end.

**Webhooks, when the receiver can expose its own endpoint.** Reach for a webhook instead of a socket when the relationship is service-to-service, delivery is best described as "the event source calls me when something happens," and the receiving system can host a reachable HTTPS endpoint of its own. A partner's booking system that wants to know the instant a shipment clears customs, and that already runs a public endpoint to receive the call, is the textbook case — no connection held between deliveries, no liveness sweep, no backpressure guard, because each delivery is its own bounded HTTP call. The cost moves to the sender's side: Chapter 2 and Chapter 24 both document that webhook deliveries aren't guaranteed to arrive in order, so a receiver that cares has to carry its own sequence number or timestamp and reorder on its own, and the sender has to own a retry-with-backoff policy and document it as carefully as the payload shape, since a failed delivery is the sender's problem to retry, not the receiver's problem to detect.

**HTTP/2 server push, which is not actually an option.** Name it directly so nobody reaches for it expecting it to work: HTTP/2 server push — a server proactively pushing a response the client didn't explicitly request, on the same connection — has been removed from Chrome and most other major browsers. It looked, for a few years, like a plausible lightweight alternative to a socket for pushing updates into a page that was already loaded. It is not a live option for browser fan-out today, and a team spending design time on it is spending that time on a dead end. If the interaction needs server-to-browser push, the live choices are a WebSocket or SSE, not HTTP/2 push.

**gRPC server-streaming, when neither end is a browser.** Reach for gRPC server-streaming instead of a WebSocket when both ends are services your own organization runs, already generated from a shared Protobuf contract. Chapter 2's example is the internal analytics service aggregating handling events across the fleet — it talks to the event source over a gRPC stream, not a socket, because neither end is a browser, both already speak Protobuf, and the call gets typed messages and HTTP/2 flow control without anyone writing either by hand. That flow control is the standout advantage over a raw socket: Chapter 12's hand-rolled backpressure guard exists precisely because WebSockets don't have an equivalent, while gRPC server-streaming gets it from the underlying HTTP/2 stream at no extra implementation cost. The trade is that neither end can be a browser without a grpc-web proxy in between, which is itself an argument against choosing this shape when a client-facing socket is actually what's needed.

**Plain request/response on demand, when nothing is actually live.** Chapter 2's decision framework starts with exactly this question — does the interaction need live updates at all — and a surprising number of interactions answer no. A report generated once a day, a page that reloads when the user clicks refresh, a settings screen that only needs the current value when it's opened: none of these need a connection held open, a reconnect policy, a liveness sweep, or a backplane. Forcing any of the five push-shaped transports onto an interaction that was never going to push anything new adds connection state for a pattern that never uses it. This is the sixth answer Chapter 2's framework resolves to, and it's the cheapest one on the list precisely because it asks for nothing beyond what HTTP already does well.

**A message broker, for backend-to-backend traffic that doesn't belong on a socket at all.** This site's own `examples/part4-backplane` is the broker alternative, not an example to contrast against it. Once Chapter 16 and Chapter 18 needed reliable, replayable, fan-out-capable delivery between services, the fix wasn't a smarter socket — it was Kafka, a topic, and consumers on each instance subscribing to it. Two backend services that need to exchange events reliably, with replay, ordering per partition, and no requirement that either side be online at the same moment as the other, should talk through a broker directly rather than through a socket connection that happens to be carrying backend traffic. The `kafka` versus `redis` toggle `examples/part4-backplane/README.md` documents makes the trade explicit: Kafka buys durability and replay at the cost of running and reasoning about a log, Redis buys nearly all of the cross-instance fan-out with a fraction of the operational surface at the cost of giving up replay entirely — but both are brokers doing backend-to-backend delivery, and neither one is a browser-facing WebSocket, because neither end here is a browser tab waiting on a live connection.

## Migration-away signals

An interaction already running on a socket is a candidate to migrate off one when any of the following holds, independent of why the socket was chosen originally:

- **Idle tabs are holding file descriptors for data that rarely changes.** A connection open for the life of a tab, watching a value that updates a handful of times a day, pays the full cost of liveness detection and connection-table pressure for updates that almost never arrive — exactly the cost Chapter 2's "when a socket is the wrong answer" section names for the booking confirmation page watching a status that changes twice a day.
- **The client-to-server channel has never carried a message.** If a socket has been live for months and the server-to-client direction is the only one that's ever used, the duplex capability that justified the socket in the first place was never exercised. That's the SSE case waiting to be noticed: `EventSource` gives up nothing this interaction has actually used.
- **The update frequency is lower than the overhead of holding the connection open.** A liveness sweep, a reconnect policy, and a backpressure guard all cost something to run continuously, whether or not an update ever arrives to justify them. When the update rate is low enough that a long-poll's per-update request cost would be cheaper in aggregate than a continuously open connection's standing cost, long-polling or SSE wins on pure economics.
- **A proxy or firewall on the path breaks the `Upgrade` handshake.** Chapter 2 already flags this as a reason to route toward SSE or long-polling at design time; the same signal applies after the fact. A socket that works in every environment the team tested but fails intermittently behind a customer's corporate network is showing exactly this failure mode, and no amount of client-side retry logic fixes a proxy that strips `Connection: Upgrade` outright.
- **Fan-out cost scales with instance count, not with subscriber count.** Chapter 24's anti-patterns chapter names this directly: a backplane with N instances subscribed does roughly N times the deserialize-and-filter work per injected event, regardless of how many of those instances actually have a client waiting. If the number of instances is growing faster than the number of connected clients per booking, the backplane's broadcast domain needs partitioning — or the interaction needs to be re-examined for whether it needed a socket-backed backplane at all, versus a narrower-scoped webhook or polling design that never had an N-instance multiplier to begin with.

## Where this goes next

This chapter is not the last one. Chapter 28 assembles the final project, and it does so by putting the socket back where it belongs — the handling-event feed needs the duplex, low-latency delivery this entire site has spent twenty-six chapters building correctly. The point of this chapter was never that a socket is wrong everywhere; it's that the decision has to be made the same way every time, for every interaction, rather than defaulted to because the rest of a WebSockets site makes it look like the obvious answer.

<div class="callout callout--safe"><p class="callout__title">Decision</p><p>A socket earns its cost only when the interaction needs low-latency, full-duplex delivery held open continuously — both sides need to send, the update rate justifies a standing connection, and the client is positioned to benefit from updates arriving in well under a second rather than on the next poll. Every other shape is cheaper on one of the six alternatives above: SSE when only the server sends to a browser tab, long-polling when the network path doesn't trust a held-open response, a webhook when the receiver can expose its own endpoint, gRPC server-streaming when neither end is a browser, plain request/response when nothing is actually live, and a message broker when the traffic is backend-to-backend rather than client-facing.
