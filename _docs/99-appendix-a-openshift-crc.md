## Learning objectives

By the end of this chapter you can:

- Explain why edge-TLS Route termination proxies a WebSocket `Upgrade` cleanly while the same termination type fails an ALPN-negotiated gRPC handshake on the identical router.
- Install an operator from OperatorHub with `installPlanApproval: Manual` and a pinned `startingCSV`, and explain what approving only that one `InstallPlan` protects against.
- Build application images inside the cluster — binary S2I for Quarkus, a Docker-strategy `BuildConfig` for Python — instead of pushing a host-built image into a registry the cluster can see.
- Verify a `wss://` connection against the cluster's own ingress CA, and reach a second instance only via `oc exec`, never a port-forward or NodePort.
- Poll a Route with `wait_route_serving` instead of trusting `oc rollout status` alone, and explain the `503` window it closes.

## Why this matters

Chapter 26 answered whether this topology survives a real scheduler; this appendix answers a narrower, platform-specific version of the same question — whether the identical four-instance, Kafka-or-Redis contract survives OpenShift's own mechanisms in place of minikube's: Routes instead of Ingress, an operator installed through OperatorHub with a pinned CSV instead of a Helm-installed upstream Strimzi, and an image assembled inside the cluster under a UID the cluster picks for itself. Every claim below is backed by a live, headless run's evidence directory, not an inference from the manifests alone.

Chapter 26 moved `examples/part4-backplane` onto Kubernetes via minikube: ingress-nginx, Strimzi-managed Kafka, a plain Kubernetes Deployment for Redis. This appendix moves the identical chart's intent — four app instances, a Kafka or Redis backplane, one externally reachable instance per stack — onto OpenShift-native mechanisms instead: Routes instead of Ingress, the AMQ Streams operator instead of Strimzi, binary S2I and a Docker-strategy BuildConfig instead of a host-built image pushed to a registry minikube can see. `examples/part4-backplane/openshift/` is the third rung on this site's runtime ladder (compose, minikube, CRC), and unlike the first two, every claim below has a live run behind it: **VERIFIED LIVE HEADLESS on CRC 2.64.0 / OpenShift 4.22.14, 2026-10-19**, evidence under `examples/part4-backplane/openshift/evidence/2026-10-19/`. `verify-crc.sh` printed `PASS` after proving a schema-valid seed frame, a 65-second idle hold, and the Ch18 cross-pod fan-out, on both stacks, over both the AMQ Streams Kafka backplane and the Helm-toggled Redis backplane, entirely through edge-TLS Routes verified against the cluster's own ingress CA.

## Same chart, OpenShift-native plumbing

The minikube path's Helm chart and this one keep the same env contract: `BACKPLANE_MODE`, `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_TOPIC`, `REDIS_URL` are the same ConfigMap keys either way (`examples/part4-backplane/openshift/helm/part4-backplane/templates/config.yaml`), so the two apps' own configuration code never has to know which cluster it's running on. The one value that differs is `KAFKA_BOOTSTRAP_SERVERS` itself — AMQ Streams names the bootstrap Service `<cluster-name>-kafka-bootstrap` exactly the way Strimzi does, but the cluster name here is `part4-backplane`, not minikube's `my-cluster`, so the hostname changes even though the naming convention doesn't.

Everything downstream of that ConfigMap is OpenShift-specific. The chart deploys four Deployment/Service pairs — `quarkus-a`, `quarkus-b`, `python-a`, `python-b` — the same split PROTOCOL.md defines for every environment this project runs on: instance A of each stack is the one with a Route, instance B is reached only by an in-cluster call. Redis ships inside the same Helm release (`templates/redis.yaml`), because there's no operator managing it on this path any more than there is on minikube; Kafka comes from `infra/kafka.yaml` and the AMQ Streams Subscription instead, installed ahead of the chart by `install-infra.sh`.

## AMQ Streams, pinned, Manual approval

OpenShift doesn't ship a Kafka operator in the box; the project installs one from OperatorHub the same way any OLM-managed operator gets installed on CRC — `infra/amq-streams-subscription.yaml` requests the `amq-streams-3.2.x` channel with `installPlanApproval: Manual` and `startingCSV: amqstreams.v3.2.1-14` pinned explicitly. `lib.sh`'s `install_operator` applies that Subscription, waits for OLM to propose an InstallPlan, and approves only the one InstallPlan that names the pinned CSV — a later InstallPlan OLM proposes on its own, for whatever newer CSV ships after this was authored, sits unapproved until someone bumps the file by hand. That's the same `Manual`-approval-plus-pinned-CSV pattern every operator this project family installs from OperatorHub uses, and the reason is the same every time: a cluster that silently upgrades its own Kafka operator between one run of this appendix and the next is a cluster whose behavior nobody asked for.

`amqstreams.v3.2.1-14` was the current newest AMQ Streams CSV as of the 2026-10-19 live run, confirmed by reading `oc get packagemanifest amq-streams -n openshift-marketplace` directly rather than assuming a version from memory. `infra/kafka.yaml` then defines a `KafkaNodePool` with both the `controller` and `broker` roles on a single replica (KRaft mode, no separate controller quorum — this proves wire behavior, not durability) plus a `Kafka` custom resource pinning `version: 4.2.0` and `metadataVersion: 4.2-IV0`. Redis in the chart stays at `8.10.2-alpine`, the same pin as compose and minikube — only Kafka's version moved, and only because of what AMQ Streams itself supports, which the next section covers.

## Images built inside the cluster, not pushed into it

Neither app image reaches this cluster from outside it. Quarkus uses the OpenShift `openshift` Maven profile (`-Popenshift`), which packages the fast-jar on the host the way any Quarkus build does, then uploads that artifact to a binary S2I `BuildConfig` that `quarkus-openshift` generates — the build itself, including laying the jar into its final image layout, happens inside the cluster, driven by the S2I builder image's own `/usr/libexec/s2i/assemble` script. Python has no S2I builder of its own, so `build-images.sh` instead assembles a throwaway build-context directory that mirrors exactly the repo-root-relative paths `python/Containerfile`'s `COPY` lines expect (the pyproject, the lockfile, the `app/` tree, the shared AsyncAPI contract, the schema-extraction script, the part-3 fixture), and hands that directory to `oc start-build --from-dir` against a Docker-strategy `BuildConfig`. Both builds push an `ImageStream` tag (`part4-backplane-quarkus:v1`, `part4-backplane-python:v1`) the Helm chart then deploys by name — no registry credentials, no `docker push`, no host container engine touched at any point. `evidence/2026-10-19/01-cluster-builds.txt` has the resulting image digests, confirmed resolvable from the in-cluster registry service address.

## restricted-v2, everywhere, no fixed UID

Every container in this chart — both app images, Redis — runs under the `restricted-v2` SCC with no `runAsUser`, `runAsGroup`, or `fsGroup` set anywhere in the chart. OpenShift assigns an arbitrary UID from the namespace's own UID range on pod admission; `evidence/2026-10-19/02-pods.txt` shows every pod in the run landing on UID `1000650000` out of the namespace's `1000650000/10000` range, with `restricted-v2` as the SCC on each one. A container whose entrypoint assumes it owns UID 1000, or writes to a path only that UID can reach, fails under this model — the fix is a writable-by-group-0 path in the image, never a pinned UID added to "make the pod start." No image in this chart needed that fix; `ubi10/openjdk-25` and the project's own Python base already tolerate an arbitrary UID with GID 0.

## Edge-TLS Routes, and the WebSocket upgrade that survives them

Host access goes through the OpenShift router exclusively — no NodePort, no port-forward, no tunnel. `templates/routes.yaml` renders a `Route` only for `quarkus-a` and `python-a` (`values.yaml`'s `route: true` flag), each with `tls.termination: edge` and `insecureEdgeTerminationPolicy: Redirect`: TLS stops at the router, the Service behind it gets plain HTTP, and plain HTTP is exactly what an `Upgrade: websocket` request already is. The router auto-detects the `Connection: Upgrade` header and proxies the upgrade through without any WebSocket-specific annotation — the same thing ingress-nginx does on the minikube path. The one annotation this Route adds beyond the minikube Ingress's shape is `haproxy.router.openshift.io/timeout: "3600s"`, HAProxy's analogue of nginx's `proxy-read-timeout`/`proxy-send-timeout` pair: without it, a long-lived, quiet WebSocket risks the router's own default idle timeout tearing the connection down regardless of what the application does.

This is the appendix's thesis, and it lands against its own negative case rather than in isolation. This site's gRPC sibling ran the identical experiment — the same CRC release, the same Route mechanism — for a gRPC service, and found edge and reencrypt termination structurally unable to complete a native gRPC client's handshake at all: reading the router's own generated HAProxy configuration there showed `fe_sni`, the shared frontend every edge-terminated Route dispatches through by SNI, binding with the literal option `no-alpn`, unconditionally, so a strict-ALPN gRPC client gets `missing selected ALPN property` before a single request byte crosses the wire — `curl --http2` against the same Route confirmed it with `ALPN: server did not agree on a protocol`. The only termination type that worked there was `passthrough`, which forces the workload to terminate its own TLS so the client and pod can negotiate ALPN directly, bypassing the router's TLS stack entirely. A WebSocket Upgrade request never triggers ALPN negotiation in the first place — it's an ordinary HTTP/1.1 request with a couple of extra headers, the protocol switch happens after the TLS handshake the router already completed on its own terms, not during it. That's why edge termination, the simplest Route type OpenShift offers, is sufficient here and insufficient there: the two protocols hit the router's TLS termination at different layers, and only one of them depends on what happens inside that handshake.

## CA-verified wss://, instance B reached by exec, never a port-forward

`verify-crc.sh` connects to instance A exclusively through its Route, over `wss://`, with the connection's TLS verified against the cluster's own ingress CA — never `-k`/`--insecure`. OpenShift Local signs its router certificate from the cluster's own ingress CA (`configmap/default-ingress-cert -n openshift-config-managed`), which sits in no public trust store, so the script extracts that CA directly from the ConfigMap and points `websocat`'s `SSL_CERT_FILE` at it. Instance B is never reached through a Route at all — every call that crosses into it goes through `oc exec` against instance A's own running pod, curling B's cluster-DNS Service name in plain HTTP (`http://quarkus-b:8080`, `http://python-b:8082`), the same in-cluster-only path PROTOCOL.md's "A is the externally reachable one" split specifies for this project's other runtimes. No port-forward, no NodePort, no tunnel anywhere in this script, by house convention.

## On the wire

The 65-second idle hold followed by a late-arriving frame, captured directly from `evidence/2026-10-19/04-verify-crc.log`, through the Quarkus Route:

```
lib.sh: ok — quarkus/kafka: Route quarkus-a carries haproxy.router.openshift.io/timeout: 3600s: '3600s'
verify-crc.sh: quarkus/kafka: connected, received the 3 seed frames; holding idle for 65s ...
verify-crc.sh: inject eventId=evt_5f145ef4d54c4dd79368618e27 bookingId=bkg_90c618e7a9ac47e0a97c1f3c43 via exec(quarkus-a)->http://localhost:8080 -> HTTP 202
lib.sh: ok — inject evt_5f145ef4d54c4dd79368618e27 via exec(quarkus-a)->http://localhost:8080 accepted: '202'
verify-crc.sh: ok — quarkus/kafka: late frame arrived after a 65s idle hold over the edge-TLS Route (haproxy.router.openshift.io/timeout: 3600s present)
```

The script confirms the annotation is actually present on the live Route before trusting it, injects the late event by `oc exec`-ing into the same pod the idle connection is attached to, and only then asserts the frame arrived on the still-open socket — not a reconnect, the same connection that sat quiet for 65 seconds. The server-side half of delivery is captured separately in `evidence/2026-10-19/05-delivered-logs.txt`, the per-stack `delivered eventId=… instance=quarkus-a` / `instance=python-a` pod-log lines read straight off each Route-facing pod — for example the cross-pod fan-out delivery `delivered eventId=evt_f117514c222941dbaa91eccf42 bookingId=bkg_1aa9ad91853b4e119a8c64ed8f instance=quarkus-a`, logged by the same pod the Route routes to.

## What broke / watch for

Four problems surfaced only once this ran against a real cluster — none of them visible from `helm lint`, `helm template`, or a `bash -n` syntax check, which is exactly why this project's status only flips to `verified` after `verify-crc.sh` prints `PASS` on an actual live run.

**The Quarkus S2I build needs the full `ubi10/openjdk-25`, not `-runtime`.** The OpenShift S2I strategy builds an image by running the *builder* image's own `/usr/libexec/s2i/assemble` script to lay the fast-jar in place. `ubi10/openjdk-25` ships that script (and `run-java.sh`); the smaller `-runtime` variant exists specifically for a Docker/Containerfile multistage `FROM` and ships neither — pointed at it as the S2I base, the build failed with `assemble: No such file or directory`. The fix was swapping `quarkus.openshift.base-jvm-image` back to the full image; the `-runtime` tag stays reserved for a future multistage Containerfile build, never an S2I one.

**AMQ Streams pins Kafka to 4.2.0, a recorded step-back from 4.3.1 on compose and minikube.** `amqstreams.v3.2.1-14` — the newest AMQ Streams CSV as of this survey — supports Kafka 4.1.0 and 4.2.0 only, read directly from the cluster-operator pod's own `kafka-images` annotation rather than assumed from release notes. Upstream Strimzi 1.3.0, which the minikube path installs directly, already runs 4.3.1; the Red Hat-built operator simply lags it. `infra/kafka.yaml` pins 4.2.0 for that reason, and the pub/sub replay and cross-pod fan-out this appendix exercises behave identically on 4.2 and 4.3 — the step-back is an operator-version floor, not a functional gap. When `amqstreams.v3.2.1-14` is superseded, the Subscription's `channel`/`startingCSV`, `install-infra.sh`'s `CSV` variable, and `kafka.yaml`'s `version`/`metadataVersion` move together, in the same commit — letting any one of those three drift ahead of the others is its own failure mode.

**`SSL_CERT_FILE` has to carry the system trust store plus the ingress CA, not the ingress CA alone.** `verify-crc.sh` exports `SSL_CERT_FILE` so `websocat` verifies the Route's edge certificate against the cluster's own ingress CA. That variable is inherited by every child process the script spawns afterward, including the schema-validation step, which fetches the `jsonschema` package metadata from pypi.org. Pointing `SSL_CERT_FILE` at the ingress CA alone made that fetch fail with `UnknownIssuer`, because pypi.org's certificate chains to a public root the ingress-CA-only bundle doesn't contain. The fix was building a combined bundle — the host's system trust store (`/etc/ssl/certs/ca-certificates.crt` or equivalent) with the ingress CA appended — so both the cluster's edge certificate and the public internet endpoint verify against the same exported variable.

**The router answers 503 for a short window after a rollout, even once `oc rollout status` has already returned.** `oc rollout status` reports success as soon as the new pods are Ready; HAProxy finishing the endpoint swap for the Route in front of them is a separate, slightly later event. The live run's Redis-backplane toggle hit this directly: the first `wss://` connect attempt right after the rollout got a router `503`, because the Route had no ready backend registered yet even though the pod behind it was. `verify-crc.sh` now has a `wait_route_serving` gate that polls the Route with a CA-verified `curl` until it returns anything other than `503` or a connection failure — a WebSocket-only path answers `404` or `426` once a backend is actually reachable — and runs that gate after both the initial deploy and the Redis-toggle rollout, before any WebSocket connect attempt.

One claim this appendix does not make stronger than it is: the 65-second idle hold is a real pass, but it's a weaker proof here than the identical check on minikube/nginx. HAProxy's own default tunnel timeout already exceeds nginx's 60-second default by a wide margin, so a quiet socket surviving 65 seconds on this path shows the connection isn't torn down and that the `3600s` annotation is actually present on the Route — it does not show that the annotation moved a timeout to an edge a real client would otherwise hit, the way the same check does against nginx's much shorter default. Both facts are true and worth keeping separate: the check passed, and it proves less on this router than it does on the other one.

## Teardown

`teardown.sh` removes the Helm release (the four Deployments/Services, Redis, both Routes, the ConfigMap), the Kafka custom resources and `KafkaNodePool` ahead of the project namespace itself, the project namespace, and the AMQ Streams Subscription/CSV/InstallPlans and the CRDs they own — in that order, because a `KafkaTopic` or `KafkaUser` finalizer left behind after the operator that manages it is already gone hangs the namespace in `Terminating` indefinitely. It inventories what's left afterward rather than assuming success, and calls `crc stop` last, leaving CRC in the same empty state it started from unless `--keep-running` is passed.

## Where this goes next

The three runtimes this Part builds — compose, minikube, OpenShift Local — now all carry the same proof: a schema-valid seed frame, a connection that survives being held quiet past any idle-detection mechanism in its path, and Ch18's cross-instance fan-out over both a durable Kafka backplane and a Redis one. What changes between them is never the application; it's always the platform's own plumbing — port-forwarding versus a Route, a Kafka pod you install yourself versus an operator-managed one, a host-built image versus one assembled inside the cluster under a UID the cluster itself picked. The four problems this appendix's live run surfaced — an S2I base image that looks interchangeable with its `-runtime` sibling until a build fails on it, an operator-imposed Kafka version floor a full minor behind the other two paths, an exported CA variable that silently breaks an unrelated outbound fetch, and a router that reports itself ready a few seconds before it actually is — are exactly the category of mistake a `helm template` dry run can never catch, because none of them are wrong YAML. They're wrong assumptions about a live system, caught only by running the live system and reading what it actually returned.

<div class="callout callout--safe"><p class="callout__title">Decision</p><p>Reach for this appendix's shape — AMQ Streams from OperatorHub with <code>Manual</code> approval and a pinned <code>startingCSV</code>, in-cluster S2I/Docker-strategy builds, <code>restricted-v2</code> with no fixed UID, edge-TLS Routes with the HAProxy idle-timeout annotation raised — whenever the target is OpenShift rather than a generic Kubernetes distribution; keep the minikube chart's env contract (the same <code>BACKPLANE_MODE</code>/<code>KAFKA_BOOTSTRAP_SERVERS</code> ConfigMap keys) so the application code never has to know which cluster it's running on. Trust edge termination for a WebSocket Route without a second thought: the Upgrade happens after the TLS handshake the router already finished on its own terms, which is exactly the hop this site's gRPC sibling found broken for ALPN-negotiated HTTP/2 and exactly the hop a WebSocket upgrade never touches. Don't trust <code>oc rollout status</code> alone as a signal that traffic can reach a workload — poll the Route itself until it answers something other than <code>503</code>. And don't let an operator's own supported-version floor drift out of step with the Subscription and the custom resource that both reference it — pin all three together, move them together, and treat the gap between this operator's Kafka version and the other two runtimes' as a documented floor, not an oversight.</p></div>
